# Учебный движок: что перенять у OpenTutor

> Статус: план изменений, код ещё не менялся. Дата: 2026-11-10.
>
> Источник идей: OpenTutor (github.com/zijinz456/OpenTutor, MIT, коммит 0e63b44).
> Берём идеи и алгоритмы, а не код: проект в основном написан ИИ, и его
> реализация FSRS использует нестандартные параметры по умолчанию.

## Зачем

CLAUDE.md §6 описывает педагогический движок: модель знаний, интервальное
повторение по FSRS, mastery по доказательствам, выбор следующего действия по
прозрачным правилам. Основа уже есть (`LearningEvent`, `SkillState`,
`help_policy`), но повторения и оценка владения пока грубые. Этот план
закрывает разрыв по частям. Каждая часть живёт сама по себе и уходит отдельным
коммитом.

## Что сейчас в коде

| Что | Где | Проблема |
|---|---|---|
| Повторение темы | `backend/mind/srs.py` (`next_review`), упрощённый SM-2: `interval_days` × `ease_factor` | Не учитывает, сколько дней реально прошло. После нескольких «не вспомнил» `ease_factor` застревает на 1,3 |
| Повторения в плане | `REVIEW_OFFSETS_DAYS = (2, 7, 21)` в `backend/studyplan/scheduling/contracts.py`, используется в `scheduling/reviews.py` | Даты не зависят от ответов ученика и не согласованы с `Topic.next_review_at` |
| История повторений | `TopicViewSet.review` в `backend/mind/views.py` меняет `Topic`, но события не пишет. `mind.ReviewLog` без пользователя и мёртвый | Без истории FSRS нельзя подстроить под учеников, а состояние нельзя пересчитать |
| Кнопки повторения | `WeakTile` в `src/components/now/side-cards.tsx`: только `GOOD` и `AGAIN` | Двух оценок мало. Страница `/dashboard/review` умеет четыре |
| Порядок тем на «Сейчас» | `rankTopics` в `side-cards.tsx`: просроченные, затем сегодняшние, затем начатые | Не видно, какую тему ученик забудет раньше |
| Оценка владения | `recompute_skill_state` в `backend/ai_engine/learning_events.py`: среднее взвешенных результатов за всю историю | Порядок попыток не важен: три старые ошибки и три свежих успеха дают то же, что наоборот |
| Признаки усталости | нет | §9.4 требует учитывать энергию, сигнала нет |

## Части

### Часть 1. FSRS вместо SM-2 и фиксированных 2/7/21 дней (согласовано)

Цель: один алгоритм повторения для темы, тьютора и плана. Дата повторения
зависит от ответов и реальной паузы.

1. **Библиотека.** Официальный пакет `fsrs` (open-spaced-repetition, MIT) в
   `backend/requirements.txt` с точной версией. Перед этим проверить его API и
   параметры по умолчанию на установленной версии. Свою реализацию формул не
   пишем.
2. **Обёртка** `backend/mind/srs.py`: та же точка входа `next_review`, внутри
   FSRS. Чистая функция: на входе прошлое состояние, оценка и момент (`now`
   аргументом), на выходе устойчивость, сложность, дата, статус темы. Статусы
   `NOT_STARTED / MEDIUM / SUCCESS / MASTERED` выводятся из устойчивости, чтобы
   страница слабых тем не сломалась.
3. **Поля `mind.Topic`:** `fsrs_stability`, `fsrs_difficulty`, `fsrs_reps`,
   `fsrs_lapses`, `fsrs_state`. `interval_days` и `ease_factor` пока остаются
   для чтения и отката.
4. **Миграция данных:** у тем, которые уже повторялись, начальная устойчивость
   берётся из `interval_days`, сложность из `ease_factor` (простое линейное
   соответствие, записать в миграции). Дата `next_review_at` не сдвигается:
   ученик не должен увидеть, что всё вдруг «пора повторить».
5. **Журнал.** `TopicViewSet.review` и `schedule_review` тьютора пишут
   `LearningEvent` с `activity="review"` и оценкой в `metadata`. Тогда состояние
   FSRS можно пересчитать из журнала, как `SkillState`, а позже подобрать
   параметры под учеников Timely.
6. **План.** `scheduling/reviews.py` ставит повторение на `Topic.next_review_at`
   (с учётом окна `REVIEW_SEARCH_WINDOW_DAYS`) вместо смещений 2/7/21.
   `REVIEW_OFFSETS_DAYS` остаётся только для темы, у которой ещё нет ни одного
   повторения.
7. **Цель вспоминания:** настройка `FSRS_DESIRED_RETENTION` (0,9 по умолчанию).
   Перед датой контрольной из `ScheduledTest` для тем этого предмета берётся
   0,95: повторения уплотняются сами.
8. **«Сейчас».** В ответе API темы появляется `recall_probability` (шанс
   вспомнить сегодня, считает backend). `rankTopics` сортирует просроченные по
   нему, а не по дате. В `WeakTile` четыре кнопки вместо двух: «Не вспомнил»,
   «С трудом», «Вспомнил», «Легко».
9. **Тесты:** таблица случаев для обёртки (новая тема, четыре оценки, повторение
   с опозданием на 10 дней даёт интервал больше, чем вовремя, серия «не
   вспомнил» не застревает); миграция; план ставит повторение на дату FSRS;
   `rankTopics` на фронтенде.

Не входит: подбор параметров FSRS по истории учеников. Это отдельная задача,
когда наберётся несколько тысяч повторений.

### Часть 2. Оценка владения с учётом порядка попыток

Цель: свежие успехи весят больше старых ошибок, и наоборот. CLAUDE.md §6.1
называет Bayesian Knowledge Tracing следующим шагом после правил.

1. В `recompute_skill_state` среднее заменяется на последовательное обновление
   вероятности владения по каждой оценённой попытке (BKT: начальная
   вероятность, шанс выучить за попытку, угадать, ошибиться по невнимательности).
   Функция остаётся чистой и пересчитывается из журнала целиком.
2. Подсказка уменьшает вес успеха, как сейчас в `_RESULT_WEIGHTS`: успех с
   подсказкой двигает вероятность вверх меньше.
3. Параметры — константы с комментарием, откуда взяты. Подбор по данным —
   потом, как в `bkt_trainer.py` у OpenTutor.
4. Пороги статусов (`MASTERY_THRESHOLD`, число самостоятельных успехов,
   системная ошибка) не меняются: статус всё так же требует доказательств
   (§6.3).
5. Тесты: «три ошибки, потом три успеха» даёт владение выше, чем «три успеха,
   потом три ошибки»; угаданный ответ не делает тему усвоенной; старые
   сценарии `test_tutor_modes.py` проходят.

### Часть 3. Проверка ответа тьютора перед показом

Цель: ловить пустые и ложные ответы детерминированно, а не надеяться на промпт.
Идея из `services/agent/verifier.py` OpenTutor.

1. Перед началом проверить, что похожего ещё нет рядом с `scrub_vendor_names`
   в `ai_engine/prompt_safety.py`.
2. Правила на русском:
   - ответ без содержания («давай разберёмся», «могу помочь»), когда ученик
     задал конкретный вопрос;
   - «в учебнике этого нет», хотя поиск по книге вернул фрагменты;
   - ссылка на страницу, которой нет среди найденных фрагментов.
3. При срабатывании: один повтор с уточнением в промпте, затем честный ответ
   «не нашёл» (§7.9). Событие пишется в журнал для метрики AI из §19.
4. Тесты на каждое правило и на отсутствие ложных срабатываний на хороших
   ответах.

### Часть 4. Сигнал усталости и перерыв

Цель: тьютор замечает «не могу», «бесит», «опять неправильно» и предлагает
перерыв или задачу проще (§9.4, §6.10). Идея из `services/agent/fatigue.py`.

1. Чистая функция в `ai_engine`: русские шаблоны плюс счёт подряд неверных
   попыток из журнала. Результат — число от 0 до 1, текст сообщения не
   сохраняется (§17.3).
2. Выше порога тьютор получает строку в контексте: предложить перерыв или
   шаг назад по лестнице помощи. Решение остаётся за учеником.
3. Родителю ничего не уходит: это не санкция и не отчёт (§10.2).
4. Тесты на шаблоны и на «спасибо, понял», которое снижает счёт.

## Позже, когда появится платформа задач (Этап 4)

Эти идеи требуют задач с проверяемыми ответами и связей между темами, которых
сейчас у `mind.Topic` нет (пререквизиты есть только у разделов книги в
`curriculum`).

- **Входной адаптивный тест** (`diagnosis/cat_pretest.py`): 5–20 вопросов,
  каждый следующий по текущей оценке уровня, стоп при достаточной точности.
  Для режима «Подготовиться» и старта новой цели.
- **Пары путаемых тем** (`loom_confusion.py`): неверный ответ совпал с
  правильным ответом соседней темы, значит темы путаются. Такие темы ставятся
  рядом в повторении.
- **Умная сессия повторения** (`lector.py`): сначала слабая базовая тема,
  связанные темы вместе, путаемые рядом, приоритет по шансу забыть из FSRS.
- **Сложность задачи по владению** (`learning_science/difficulty_selector.py`):
  ниже 0,4 базовые задачи, до 0,7 на применение, выше — с ловушками.
- **Ранжирование «что делать в свободное время»** (`agent/agenda_ranking.py`):
  когда в плане нет блока, правила без модели выбирают одно действие: проваленное
  дело, близкий дедлайн, тема на грани забывания, слабая тема.

## Что не берём

- `block_decision`: перестраивает блоки интерфейса сам и противоречит принципу
  «один следующий шаг».
- Интеграцию с Canvas и парсинг сайтов: в СНГ этих школьных систем нет.
- Их оценку поиска: `curriculum/gold_set.py` и `curriculum_retrieval_eval` уже
  строже.
- Их реализацию FSRS: берём официальный пакет.

## Порядок и правила работы

1. Часть 1, затем 2, затем 3 и 4 (последние две независимы).
2. Каждая часть — один коммит в `main` после «да» владельца, пуш тоже после
   «да». PR не делаем. Перед коммитом одно ревью.
3. Чужие незакоммиченные файлы не трогать, `git add` только по файлам части.
4. `manage.py` в `backend/` репозитория не запускать. Тесты по схеме из
   памяти проекта: Python 3.12, временный Postgres.
5. После Части 1 обновить CLAUDE.md §6.6 и §20 (повторения на FSRS).

## Открытые вопросы

- Подписи четырёх кнопок повторения: предложены выше, нужно согласие.
- Цель вспоминания перед контрольной: 0,95 или спрашивать ученика.
- Показывать ли ученику «шанс вспомнить» числом. Предложение: нет, только
  порядок тем (§6.1: внутренние числа наружу не показываются).
